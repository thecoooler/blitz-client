# Расчёт ТТХ ангара: Tanks Blitz 26.10.0

Для Leopard 1 цепочка подтверждена машинным кодом установленного клиента:

```text
экипаж 100%, амуниция отсутствует
нормализованный уровень = 100 / 100 = 1
эффективность командира = 0.57 + 0.43 × 1 = 1
эффективность заряжающего = 0.57 + 0.43 × (1 + 1 / 10) = 1.043
досылатель: множитель = 1 + (-7) / 100 = 0.93
перезарядка = (0.93 / 1.043) × 6.5 = 5.7957813998… с
округление до 2 знаков → 5.80 с

ДПМ = 360 × (60 / неокруглённая_перезарядка)
    = 3726.848635…
округление до 0 знаков → 3727
```

Это не `ceil(3726.34)`: исходное неокруглённое значение другое. Константы
`0.875` / `0.00375` не используются в найденном расчёте мастерства этой версии.
Из XML прочитаны `reloadTime=6.5` и урон базового снаряда `360`.

## Экипаж, константы и досылатель

Для отдельных членов экипажа с одинаковым мастерством:

```python
level = (mastery + crewLevelIncrease) / 100
commander = 0.57 + 0.43 * level
other_role = 0.57 + 0.43 * (level + level / 10)
```

Константы лежат по адресам `0x1048dd108` (`float32(0.43)`),
`0x1048dd10c` (`float32(0.57)`), `0x10481ac68` (`10.0`),
`0x10481d228` (`100.0`). В `0x1008fe62c` видны деление `level / 10`,
сложение с `level`, умножение на `0.43`, прибавление `0.57`.

Это формула для конфигурации Leopard 1: отдельные commander, gunner, driver,
loader; командир дополнительно выполняет роль radioman. Для совмещённых ролей
в `0x1008fe980` код делит сумму вкладов на количество членов экипажа,
выполняющих эту роль. Член экипажа с основной ролью commander вносит `commander` также во все
свои дополнительные роли. Остальные члены вносят `other_role` во все свои роли.
Если роль выполняют несколько человек, складываются их вклады и сумма делится
на число этих людей. Это усреднение людей, а не названий ролей; два самостоятельных
заряжающих дают ту же эффективность, что один. Командир-заряжающий и отдельный
заряжающий при 100% дают `(1 + 1.043) / 2 = 1.0215`.
Подтверждение: копирование эффективности командира в его дополнительные роли
`0x1008fe542–0x1008fe5ac`, выбор вклада `0x1008fe86c–0x1008fe980`,
суммирование `0x1008fe700–0x1008fe70c`. В этой функции не найден clamp
мастерства к 100%: `crewLevelIncrease` применяется **до** деления на 100.
Это не доказывает допустимость любых уровней на стороне сервера.

`XML/item_defs/vehicles/common/optional_devices.xml:8` задаёт досылатель как
`StaticFactorDevice`, атрибут `miscAttrs/gunReloadTimeFactor`, `percent=-7`.
Расчёт `0x1008ff2f0` берёт этот процент из карты модификаторов и эффективность
роли `loader` из карты экипажа:

```python
reload_scale = (1 + reload_percent / 100) / loader_efficiency
reload = reload_scale * gun.reloadTime
```

У обычного орудия без особой механики это вся цепочка reload. В той же функции
есть дополнительные ветки для специальных множителей и нескольких времён
перезарядки; они сохранены в выдержке дизассемблера.

## Скорострельность, ДПМ и округление

Помощник `0x1010c8ff0` принимает descriptor орудия и `reload_scale`. Для
обычного орудия с одним выстрелом он сводится к:

```python
shots_per_minute = 60 / (reload_scale * gun.reloadTime)
dpm = shell.damage * shots_per_minute
```

ДПМ рассчитывается заново из descriptor и коэффициента в `0x100900380`,
а не из уже округлённого UI-reload. Ветви для очереди/барабана учитывают
количество снарядов и интервалы; помощник воспроизведён в Python.

Помощник округления `0x100fec530` добавляет половину шага со знаком исходного
числа. Затем отделяет целую часть от дробной, округляет дробную часть вниз
после масштабирования и собирает число обратно. Для обычных положительных
ТТХ это округление к ближайшему с половинами вверх, а не постоянный `ceil`.
Порядок операций с `float32` сохранён в `ui_round` реконструкции.

Числа при воспроизведении порядка SSE-операций:

```text
loader = 1.0429999828338623
reload = 5.79578161239624       → 5.80
dpm    = 3726.848388671875      → 3727
```

Последние биты отличаются от формул в начале документа, вычисленных в double.
На показанные значения это не влияет. Подмена констант или промежуточное
округление при расчёте ДПМ не нужны.

## Полное время сведения

Функция `0x1008ffd70`, результат `data+0xbc`; getter `0x1008d1010`
связан с `gunAimingTime`. Сокращённая эквивалентная формула:

```python
rotation_bloom = chassis.vehicleRotation * chassis.rotationSpeed
turret_bloom = gun.turretRotation * turret.rotationSpeed
movement_bloom = chassis.vehicleMovement * min(maxFrontSpeed_mps, 8.3334)
stabilization = 1 + additiveShotDispersionFactor_percent / 100
bloom = sqrt(1 + stabilization**2 * (
    rotation_bloom**2 + turret_bloom**2 + movement_bloom**2))
aim_speed_factor = 1 + gunAimingTimeFactor_percent / -100
full_aim = (gun.aimingTime / gunner_efficiency / aim_speed_factor) * log(bloom)
```

Машинный код использует эквивалентные `logf(1 / bloom)` и отрицательное
`-aimingTime`. Скорости вращения читаются из переданных **descriptor** ходовой и башни,
а не из итоговых `chassiRotationSpeed` / `turretRotationSpeed` ангара.
**Происхождение значения descriptor перед вызовом полностью не установлено:**
старое утверждение, что оно обязательно равно исходному XML, было слишком сильным.
Ниже отдельно разобраны подготовка данных и несовпадение с игрой.
Скорость движения — м/с. Константа ограничения — именно `float32(8.3334)`
(`0x1048dd134`), не точное `30 / 3.6`.

Для Leopard 1 без прочих модификаторов: `54 × 0.1`, `36 × 0.05`,
`min(65 / 3.6, 8.3334) × 0.1`, `aimingTime=2.3`, gunner `1.043`:
`full_aim ≈ 3.891184` → **3.9 с**.

В `0x1008ff2f0` также рассчитывается стационарный разброс:
`shotDispersionRadius × (1 + shotDispersionAngleFactor_percent / 100) / gunner`.
Парсер сначала делит XML-radius на 100 (`0x1010c7f6f`), расчёт умножает
его на 100 обратно. Без других бонусов: `0.3 / 1.043 ≈ 0.287632` → **0.288**.

## Проходимость

Функция `0x1008ff660` сначала считает сопротивления грунтов:

```python
effective_resistance[i] = (
    chassis.terrainResistance[i]
    / (1 + terrain_bonus_percent[i] / 100)
    / driver_efficiency
)
permeability_percent[i] = 100 / effective_resistance[i]
```

Эффективные firm/medium/soft resistance записываются в `data+0x28/0x2c/0x30`.
Проходимость до преобразования в проценты — в `data+0x34/0x38/0x3c`.
`terrainPermeabilityFirm/Medium/Soft` используют последние поля.

Для Leopard 1, `terrainResistance = 0.6 0.7 1`, driver `1.043`, без прочих
бонусов: **174% / 149% / 104%** после округления.

## Поворот корпуса

Функция `0x1008ffb90`, результат `data+0x94`, ключ `chassiRotationSpeed`:

```python
rotation = chassis.rotationSpeed * (1 + rotationSpeedFactor_percent / 100)
hull_rotation = (
    rotation
    * current_engine_power / reference_engine_power
    * reference_mass / current_mass
    * reference_medium_resistance / current_effective_medium_resistance
    * (1 + driver_rotation_skill * 0.01)
)
```

Здесь `reference` — первые элементы списков модулей машины. Код суммирует
массу корпуса, ходовой, двигателя, бака, башни и орудия этой конфигурации.
Это следует из обращений к спискам модулей `0x1008ffbb6`–`0x1008ffbdc`
и суммирования `0x1008ffcfa`–`0x1008ffd12`.
Мастерство driver уже входит в effective resistance: повторно умножать на
его эффективность не нужно. Последний множитель связан с отдельным навыком
`virtuoso` (ключ по адресу `0x104971a20`), получаемым из данных аккаунта;
при отсутствии этого вклада он равен 1.

У Leopard 1 в XML по одному варианту модулей, поэтому без других модификаторов
отношения мощности и массы равны 1, а отношение сопротивлений равно `1.043`:
`54 × 1.043 = 56.322` → **56.32°/с**.

## Воспроизведение и границы

```sh
python3 scripts/reproduce-hangar-ttx.py
```

Скрипт выводит исходные float32 и строки UI для reload, ДПМ, полного сведения,
поворота, разброса и трёх грунтов. Пример предполагает досылатель -7%,
100% экипаж, отсутствие амуниции, остальных модификаторов и вкладов отдельных
навыков. Для полного сведения `logf` приближён через округлённый в float32
`math.log`; побитовая эмуляция системной libm не заявляется.

Это исследовательская реконструкция конкретной версии клиента, не подключённый
к экспорту универсальный калькулятор. При другой версии бинарника нужно заново
проверять адреса, константы и расположение полей.

Повторная проверка 20 октября 2026: установлен тот же **26.10.0 x86_64**, SHA-256
`94de0345b00322fc9036105f477075f867eefa3d7cdddefe22423822c9fd69e2`.

инициализатор `0x10093b830` и его ссылки на строковые литералы.

Разделяем четыре уровня проверки:

- **Бинарник:** арифметика перечисленных функций, роли и обращения к полям.
- **Внутри процесса игры:** новых измерений нет. Получить список процессов в

- **Гипотеза:** подстановка driver × virtuoso в поле ходовой для полного сведения.
  Совпадение четырёх результатов не повышает её до доказательства.

Значения 37,55; 10,70; 10,51; 4,1/3,8 предоставлены пользователем как наблюдения
в игре; в этом исследовании они независимо внутри игры не измерялись.
Ни скриншоты, ни сайты источником коэффициентов не служили.

## Поворот башни

`0x1008feb6a–0x1008febd3` внутри `0x1008fea10`:

```text
turret = context+0x48
base = float(turret+0x1a0)
percent = modifiers["turretRotationSpeedIncrease"]   # отсутствует → 0
result = (base × (1 + percent / 100)) × crew["gunner"]
store result → data+0x50
```

Ключ модификатора — глобальная строка `0x10544c8a8`, её литерал
`0x1046bbca3`. Роль — **gunner** (`0x1049728f8`); `commander`
(`0x1049728c8`) используется отдельно, например для обзора в `0x1008fef2a`.
Единицы показателя — °/с, `digits=2`.

У Leopard 1 gunner отдельный: `36 × float32(1.043) = 37.54800033569336` →
**37,55°/с**. Командир-радист остаётся с эффективностью 1,0.
Для совмещённого gunner применяется описанное выше среднее вкладов людей.
Экипажная амуниция меняет `crewLevelIncrease`; непосредственный бонус башни
суммируется под ключом `turretRotationSpeedIncrease`, затем умножается на gunner.
Оборудование improvedControls имеет другой ключ, `rotationSpeedFactor`, и
в этой ветке башни не читается. «Всё слева» нужно разрешать по preset машины,
а не по глобальному списку устройств.

В ветке башни нет чтения навыка, уровня VII, HP, числа противников или времени
после выстрела. Следовательно, добавлять к ней все условные боевые навыки
автоматически нельзя. Это утверждение о найденной ангарной ветке; влияние
условия через ещё не исследованный поставщик модификаторов отдельно не исключено.

## Полное сведение: прослеженная подготовка и оставшийся пробел

Прослеженная цепочка:

1. Парсер `0x1010bf6f4` сравнивает `rotationSpeed`; `0x1010bf987–0x1010bf98f`
   вызывает чтение float и записывает его в chassis+0x1a8.
2. Конструктор `0x1008fdd60` сохраняет входные сервисы и вызывает `0x1008fdae0`.
   Последний выбирает указатели на модули: при ненулевом флаге — первые в списках,
   иначе — выбранные из конфигурации (`0x1008fdb2e–0x1008fdb66`).
   Затем `0x101453060` предоставляет карту, из которой возможна замена указателей
   (`0x1008fdc7c–0x1008fdca1`); для орудия есть дополнительное разрешение внутри башни.
   **Нельзя считать любые эти указатели заведомо исходными XML-объектами.**
3. `0x1008fde20` объединяет три входных списка объектов и собирает карту
   модификаторов в context+0x58; `0x1008fe0c0` складывает вклады одного ключа.
   Записи в chassis+0x1a8 в этой функции не обнаружено.
4. `0x1008fe3a0` заполняет отдельную карту эффективностей context+0x70;
   затем `0x1008fea10` вызывает terrain, camouflage, hull rotation и full aim.
5. **`0x1008ff7c0` — маскировка.** Её `+0x1a8` относится к **descriptor машины**:
   `context → +0x0 → +0x8 → +0x10 → +0x1a8`, а не к `context+0x30` (ходовой).
   Это `camouflageBonus`; поле не переписывается функцией.
6. `0x1008ffb90` вычисляет конечный поворот корпуса в **data+0x94** с мощностью,
   массой, сопротивлением и virtuoso. Он не записывает результат в chassis+0x1a8.
7. `0x1008ffd96–0x1008ffdbf` читает ходовую из context+0x30, затем +0x1a8;
   читает скорость башни из turret+0x1a0. Ни data+0x94, ни data+0x50 здесь не читаются.

Таким образом, формула тела `0x1008ffd70` подтверждена, но гипотеза о
**предварительно изменённом поле ходовой** пока не подтверждена. Следующий
необходимый шаг — остановиться на входе этой функции в работающем ангаре,
снять `*(float*)(*(uintptr_t*)(context+0x30)+0x1a8)`, указатель descriptor,
карты context+0x58/+0x70, data+0x94 и значение virtuoso. Затем сопоставить
указатель с выбранной ходовой и результатом `0x101453060`, поставить watchpoint
на это поле от момента создания/замены descriptor до расчёта. Нужны реальные
состояния четырёх конфигураций, а не только итоговая UI-строка.

Численный эксперимент (гипотеза, **не итоговая подтверждённая поправка**):

```python
rotation_input = (54 * driver_efficiency) * (1 + 0.01 * virtuoso_level)
# при driver=1.043, virtuoso=7, aiming_time_percent=0:
# full aim = 4.1013150215 → 4.1; stabilization=-15: 3.7531499863 → 3.8
```

В [скрипте](../scripts/reproduce-hangar-ttx.py) эти четыре строки явно помечены
`HYPOTHESIS`. Обе конфигурации мобильности в этом эксперименте используют один
вход: именно это предположение проверяется. Оно не доказывает отсутствие
влияния оборудования на descriptor. Пример с исходными 54 даёт 3,9/3,5 с и
оставлен как видимое несовпадение, а не выдан за расчёт игры.

**Driver ≠ отношение сопротивлений:**
`raw_medium / effective_medium = driver × (1 + medium_bonus/100)`.
При нулевом бонусе эти величины совпадают; при бонусе проходимости расходятся.
Поэтому даже снятое значение 60,26454 само по себе не различит две модели.
Для различения нужен дополнительный опыт с бонусом средней проходимости.

Матрица пользователя не задаёт остальные устройства явно. В гипотезном
численном примере принят `gunAimingTimeFactor=0`. Если выбран enhancedAimDrives,
его `-10` обязательно делит время ещё на 1,1: это уже другая конфигурация.
Название «сбалансированное орудие» нельзя молча отождествлять с XML-ключом без
проверки выбранного предмета/preset.

## Сочетание модификаторов и порядок операций

Общий подтверждённый уровень — **уже разрешённая карта модификаторов**.
`0x1008fde20` и `0x1008fe0c0` суммируют float32-вклады одинакового ключа:
`percent = ((0 + p1) + p2) + …`. Поэтому -10 и -5 одного ключа дают -15,
а не последовательное умножение на 0,9 и 0,95. Разные ключи затем читаются
отдельными расчётами. Типы `StaticFactorDevice`, `StaticAdditiveDevice`,
`StaticPhysicsAttrsModifier`, `RecycledEngine` нельзя смешивать только по имени
поля в `display_params`: значимы `script`, фильтры класса/машины/режима и
условия источника. Полный интерпретатор всех скриптов предметов не восстановлен.

Здесь `F(p)=float32(1 + float32(p/100))`, `E(role)` — средняя эффективность,
`P(key)` — суммарное значение ключа; `R_i` — сопротивление.

| Показатель | Порядок вычисления | Код |
| --- | --- | --- |
| Мастерство | `(mastery + P(crewLevelIncrease))/100`, затем командир/остальные, затем среднее по роли | `0x1008fe3a0` |
| Мощность | `engine.power × F(P(enginePowerIncrease))`; прямого множителя driver нет | `0x1008fed02–0x1008fed4f` |
| Обычная перезарядка | `scale=F(P(gunReloadTimeFactor))/E(loader)`, затем `scale × reloadTime` | `0x1008ff2f0` |
| Стационарный разброс | `(radius/100 × 100) × F(P(shotDispersionAngleFactor)) / E(gunner)` | `0x1008ff4a3–0x1008ff514` |
| Сведение | `(-aimingTime/E(gunner))/(1+P(gunAimingTimeFactor)/(-100)) × logf(1/bloom)` | `0x1008ffd70` |
| Динамический разброс | квадраты трёх произведений → сумма → `F(P(additiveShotDispersionFactor))²` → `+1` → sqrt | `0x1008ffe90–0x1008ffee7` |
| Грунт | `(raw_R × (1/F(P(terrain_bonus_i)))) / E(driver)` | `0x1008ff660` |
| Корпус | rotation modifier → power ratio → mass ratio → medium resistance ratio → `1+0.01×virtuoso` | `0x1008ffb90` |
| Башня | rotation modifier → `E(gunner)` | `0x1008feb6a` |

Для обычных процентов карта не обрезается в перечисленных ветках. Ограничения
допустимых предметов, мастерства и уровней принадлежат входным данным; нельзя
на основании этого разрешать нулевые знаменатели или вымышленные комбинации.
В full aim есть **min(speed, float32(8.3334))**; в средней скорости — min с
максимальной скоростью. В промежуточных вычислениях не найдено десятичного
округления UI. Оно выполняется в конце отдельно для каждого getter.
Исключения, видимые в коде: HP округляется до целого в `0x1008fea7c–0x1008fea97`;
число групп снарядов — `ceil(clip.count/burst.count)` в `0x1008ff3cd–0x1008ff3db`.
Скорострельность при этом использует float-отношение, а не округлённое число групп.

Амуниция с crewLevelIncrease складывается с вентиляцией до расчёта экипажа;
амуниция с бонусом мощности попадает в соответствующий ключ карты. Их эффекты
перемножаются с прочими факторами только там, где это делает конкретная формула.
Условные эффекты «при малом HP», «после попаданий», «рядом противники» не следует
включать в обычное ангарное значение только потому, что навык изучен до VII.
Прямо найдены чтения **camouflage** и **virtuoso** через аккаунт/сервис навыков
(`0x1008ffa0d`, `0x1008ffc59`); эта ветка использует уровни с коэффициентами
**0,03** и **0,01**, зашитыми в бинарнике. Параметры `*PerLevel` из avatar.xml
полезны для проверки, но сами по себе не доказывают применение в ангаре.

## Заряжающие и многозарядные орудия

При 100%, без амуниции, досылатель -7%:

| Машина | Вклад loader | Реконструкция float32 → UI | Контроль игры |
| --- | --- | --- | --- |
| ИС-7 | отдельные заряжающие: среднее 1,043 | `12 × (0.93/1.043)` → 10,70 с | 10,70 с |
| Grille 15 | commander совмещает loader: 1,0 | `11.3 × (0.93/1)` → 10,51 с | 10,51 с |

Точные XML-схемы экипажа сохранены в configuration; одинаковые primary-роли
нельзя терять при преобразовании в словарь. У ИС-7 повторяются `loader`,
у Grille 15 `commander` имеет текст `loader`.

`0x1010c8ff0`: обозначим `B=burst.count`, `C=clip.count`,
`tB=burst interval`, `tC=clip interval`, `T=reloadTime`, `s=reload_scale`.
Интервалы в секундах; count ≥ 1 для обычных валидных descriptor.

```text
q = C / (B if C >= 2 else 1)          # float32, не целочисленное деление
intervalB = tB if B >= 2 else 0
intervalC = tC if C >= 2 else 0
rpm = ((B × q) × 60) / (((s × T) + ((B-1) × intervalB))
                        + ((q-1) × intervalC))
dpm = damage × rpm
```

Множитель loader/досылателя применяется к `T`, но не к обоим интервалам в этом
помощнике. XML `clip.rate` и `burst.rate` парсер переводит в интервалы как
`60/rate`: `0x1010c773c–0x1010c7754`, `0x1010c7893–0x1010c78ae`.
**Не передавать rate напрямую как секунды.** `gun+0x1d0` — burst,
`gun+0x1d8` — clip. Искусственные исполняемые примеры:

| Механика | Descriptor | Снарядов/цикл; длительность | rpm |
| --- | --- | --- | --- |
| Барабан | C=3, B=1, T=20, tC=2 | 3; 24 с | 7,5 |
| Очередь | C=1, B=2, T=10, tB=0,5 | 2; 10,5 с | 11,428572 |
| Вместе | C=4, B=2, T=20, tC=2, tB=0,5 | 4; 22,5 с | 10,666667 |

Это описание **ангарного помощника**, не утверждение о полной боевой симуляции
всех сочетаний. Особые ветки `gun+0x1e0/+0x1e8`, флаги optional float,
несколько времён reload (`data+0xac/+0xb4`) и массив `gun+0x220` видны в
`0x1008ff36e–0x1008ff47a`, `0x1008ff51c–0x1008ff5f8`.
Их нельзя автоматически обобщать на дозарядку, резервный снаряд, ускоренную
дозарядку или другие механики: ещё нужно сопоставить типы descriptor, конкретную
машину и выбранный getter. Отдельного подтверждённого калькулятора этих механик нет.

## Средняя скорость

В `0x1008fef88–0x1008ff025` восстановлена ангарная оценка; это не средняя
скорость на конкретной карте. `power` в data+0x8c — Вт, `mass` в data+0 — кг,
`R` в data+0x2c — эффективное сопротивление среднего грунта.

```text
x = (power / 735.5) / (mass / 1000)       # л.с./т
r = (1 - R) / 0.1
z = ((x × -0.0371) + 1.3115) × r + x
if z > 0:
    speed_kph = powf(z, 0.5225) × 7.5587
else:
    speed_kph = runtime_config_fallback
avg_mps = min(speed_kph × 0.27778, max_forward_mps)
```

Все литералы — ближайшие float32; адреса `0x1048dd11c–0x1048dd12c`;
переводы мощности/массы — `0x1048dd0f0/+4`. Числа не подбирались под Leopard.
Парсер двигателя `0x1010c5e1c` переводит XML power из л.с. в Вт множителем
735,5. Конечный getter/UI переводит м/с в км/ч и округляет `avgSpeed` до целого.
При `z<=0` код берёт поле конфигурационной модели через `0x1008a9ed0`,
результат+0x18; источник его заполнения ещё не прослежен. Скрипт требует явного
fallback для этой ветки, не задаёт его константой. Влияние экипажа здесь косвенное,
через сопротивление; явного чтения «surrounded_by_enemy» в этой ветке нет.

## Маскировка

`0x1008ff7c0` вычисляет **доли**, перевод в проценты — отдельный шаг UI.
В обычной ветке `vehicle+0x1a0= moving`, `+0x1a4=still`,
`+0x1a8=camouflageBonus`; последнее поле не имеет отношения к chassis.rotationSpeed.
`gun+0x218` — invisibilityFactorAtShot. `firePenalty` не надо подставлять сюда
вместо camouflageBonus или множителя орудия.

```text
c = разрешённый camouflageBonus
n = P(detectabilityFactor)
k = float32(level(camouflage) × 0.03)
still_final  = ((still + c) + (n+n)) + k      # data+0x9c
moving_final = ((moving + c) + n) + k          # data+0xa0
shot_factor = gun.invisibilityFactorAtShot × (1 + P(invisibilityFactorAtShot)/-100)
after_shot = still_final × shot_factor        # data+0xa4
```

Это буквально ангарные операции: detectabilityFactor здесь **аддитивная доля**,
а не процентный множитель от базовой маскировки; не заменять их привычной боевой
формулой. `invisibilityFactorAtShot` из карты, наоборот, процент, знак знаменателя
отрицательный. В найденной ветке нет clamp к [0;1]. Сведения о боевой маскировке,
растительности и коэффициенте после выстрела на ходу из неё не следуют.

При наличии сервиса context+0x18 бонус `c` может заменяться через виртуальные
вызовы +0x70/+0x68 либо +0x30 и `0x1010b0ba0`; их входы связаны с выбранным
оформлением. Поэтому для **итоговой** маскировки нужен реально разрешённый бонус
камуфляжа, а не безусловный ноль. Пример c=0, без сети, skill VII для Leopard:
45,7% покой, 39,5% движение, около 9,5513% после выстрела (орудийный factor 0,209).
Это отдельная реконструкция ветки, не новая контрольная точка из игры.

## Углы: что объединяет ангар

`0x1008febd8–0x1008fecfd` использует ориентацию корпуса из runtime-конфигурации
и пределы **выбранного орудия** `gun+0x170/+0x174`, а не минимум всех XML-полей.
Для quaternion `(x,y,z,w)` из +0x58/+0x5c/+0x60/+0x64:

```text
pitch = atan2f(2*x*w + 2*y*z, 1 - (2*x*x + 2*y*y))
lower = gun.lowerPitch - P(lowerPitchLimitIncrease)*pi/180 - pitch
upper = gun.upperPitch + P(upperPitchLimitIncrease)*pi/180 - pitch
span = upper - lower
```

Радианы; константа градусов в радианы `0x1048c7d00`.
`data+0x7c/+0x80` — signed lower/upper, +0x84 — abs(lower), +0x88 — upper,
+0x78 — span. Парсер орудия переводит пределы из XML в радианы.
Горизонтальные пределы читаются из **башни** `turret+0x148/+0x14c`;
для отсутствующих ограничений используется полный круг `float32(2*pi)`;
порог sentinel — `-100499` (`0x1048dd114`). При двух заданных границах span=upper-lower.
Границы/abs(lower)/upper записываются в data+0x68/+0x6c/+0x70/+0x74.

Произвольный азимут, маски ограничений корпуса/башни и зависимость склонения
от направления эта ангарная ветка не объединяет. Для калькулятора полного
контура доступных углов нужен отдельный разбор боевого ограничителя и парсеров
сложных pitch/yaw limits; исходные поля должны оставаться в экспорте.

## Достаточность data.json и ограничения поставщиков

Добавлено необязательное поле **hangarParameters**: исходный
`Data/hangarParamsConfig.yaml`, без изменения keyedArchive, digits, units и
неизвестных полей. Читается только при `include=data`, при отсутствии опускается,
использует обычный overlay Data/packs. Тест `TestHangarParametersExport` проверяет
приоритет packs, точность digits и сохранение null, а также отсутствие поля при
экспорте только icons. Схема version=1 допускает новые поля.

Уже имеющихся configuration/components достаточно для crew, порядка reference
модулей, базовых power/weight/resistance, clip/burst/rate, invisibility и углов.
settings, equipment, provisions и crewSkills сохраняют определения бонусов.
**Исходные параметры не переписаны эффективными значениями.** Константы 0,43,
0,57, формулы средней скорости и навыковых ангарных веток принадлежат
исполняемому коду, а не дополнительной таблице ресурсов: они явно записаны
в этой версии реконструкции и в дампе констант, не замаскированы под XML-настройки.
Переносить их на другую версию клиента без повторной проверки нельзя.

Не хватает для полностью автономного калькулятора:

- разрешения всех script-типов в карту ангарных модификаторов, выбранного режима,
  серверных переключателей и реально активных условных эффектов;
- уровней навыков/мастерства конкретного аккаунта, выбранного камуфляжа и
  runtime-бонуса оформления; экспорт определений не является экспортом состояния;
- источника fallback средней скорости при z<=0;
- подтверждённого происхождения chassis+0x1a8 на фактическом пути полного сведения;
- интерпретации специальных reload descriptor и сложного боевого контура углов.

Текущий `--server-config` экспортирует только экономику обучения из локального
серверного кеша. Эти файлы не доказывают активность навыка/эффекта и не подменяют
состояние процесса. Для перечисленных неизвестных не найден доказанный серверный
ключ: происхождение нельзя без проверки объявить «точно серверным». Если сервис
возвращает серверную настройку, следующий шаг — проследить её загрузчик и точный
ключ; пока значение отсутствует, оно не заменяется предположительным.

## Проверка и итог для калькулятора

```sh
python3 scripts/reproduce-hangar-ttx.py
python3 -m unittest discover -s scripts -p 'test_reproduce_hangar_ttx.py'
go test ./export
```

Тесты проверяют 37,55 / 10,70 / 10,51, float32 и UI rounding, совмещённых/двух
заряжающих, суммирование процентов, различие driver и грунтового отношения,
циклы барабан/очередь/вместе, границы скорости и маскировки. Гипотезные 4,1/3,8
проверяются отдельно с явным названием; это не регрессия подтверждённой игры.
Для `logf`, `powf` используется math с округлением результата в float32:
побитовое совпадение системных libm не гарантируется.

Достоверно можно реализовать **вычислительное ядро при известных разрешённых
входах**: экипаж по людям/ролям, обычный reload/DPM, данный помощник clip/burst,
башню, стационарный разброс, грунты, корпус, основную ветку средней скорости,
описанную ветку маскировки и простые ангарные углы. Полное сведение нельзя пока
объявить достоверным по одному XML: требуется измерение descriptor и его
поставщика. Условные эффекты, специальные перезарядки, оформление и сложные
ограничения углов требуют следующих отдельных трассировок.
